The Log Forwarding That Never Worked: AppArmor and rsyslog's RELP+TLS

Posted Nov 24, 2026
By Lee, Chien-Pang
7 min read

The Log Forwarding That Never Worked: AppArmor and rsyslog's RELP+TLS

As one of my security lockdowns for running systems, I adopted AppArmor, a Linux Security Module (LSM) that provides mandatory access control (MAC) for applications, to fortify the system’s protection in several respects. As usual, all was good until I trod, once again, on the hard-to-avoid trade-offs of enforcing security hardening.

I added a cluster log: every node forwards its security-relevant syslog lines to every control node over RELP with TLS, using the cluster’s own CA, with a disk-backed queue so a peer’s reboot loses nothing. The config generator rendered imrelp and omrelp blocks, the unit tests pinned the rendered config, an end-to-end test checked that a message from a member showed up on the control node. Green, merged, forgotten.

Then I added a stricter check to my test pipeline: the boot journal of a freshly installed node must have no unexplained error line. It went red on the first run, and the lines it found were rsyslog’s:

h1 audit[7356]: AVC apparmor="DENIED" operation="open" class="file" profile="rsyslogd" name="/etc/frad/ca/ca.crt" ... requested_mask="r"
h1 audit[7356]: AVC apparmor="DENIED" operation="open" class="file" profile="rsyslogd" name="/etc/frad/ca/rsyslog.key" ... requested_mask="r"
rsyslogd: imrelp[2514]: error 'Failed to set certificate trust files [gnutls error -64: Error while reading file.]'
rsyslogd: action-8-omrelp queue: error creating disk queue - giving up.
rsyslogd: $WorkDirectory: /var/lib/rsyslog can not be accessed

Nine denials on the CA certificate, six each on rsyslog’s own cert and key, and a disk queue that could not be created. The forwarding had never worked on any node. Not since the day I merged it.

How did the test pass, then?

Ubuntu ships rsyslog with an AppArmor profile, usr.sbin.rsyslogd, and the image enforces it. The profile knows the paths rsyslog normally touches: /var/log, /var/spool/rsyslog, the package’s own config. It knows nothing about /etc/frad/ca/, because no stock rsyslog reads a certificate from there. So imrelp could not load its trust files and gave up with gnutls error -64, which is gnutls for “could not read the file” and says nothing about why.

How the end-to-end test had been green I honestly cannot reconstruct from my notes; the lockdown of the image and the forwarding feature went in weeks apart, each tested on its own, and my best guess is that the test ran before the profile was enforced for rsyslog. The unit tests pinned the rendered config, which was correct. Nothing in the pipeline had asked whether the daemon was actually allowed to do what the config told it to, until the journal check did.

Two errors, one lead too many

The AppArmor part was quick to fix. The package profile has an include hook inside its body, include if exists <rsyslog.d>, meant exactly for this: a drop-in file in /etc/apparmor.d/rsyslog.d/ with the extra rules, installed by the image build, never touching the package’s own file.

# cluster log over RELP+TLS: cluster CA certs, receiver dir
/etc/frad/ca/ r,
/etc/frad/ca/** r,
/reserve/log/ r,
/reserve/log/** rwk,

apparmor_parser -Q -K on the image’s profile tree confirmed the rules landed in the profile, and the next boot journal had no denial on the certificates. I had expected the disk queue error to go with them: a queue that fails to initialise after a TLS failure looks like a follow-on. It stayed.

Second lead, also wrong: on my build host /var/spool/rsyslog is owned by messagebus, which looked like a uid mix-up in the image. It is uid 101, and uid 101 in the image is syslog. The host’s ls -l was lying about a file system that was not its own.

The real cause was in my own rendered config, one line I had copied from an example:

1

global(workDirectory="/var/lib/rsyslog")

/var/lib/rsyslog does not exist in the image. Ubuntu’s rsyslog uses /var/spool/rsyslog, and that is the only directory the package profile lets rsyslogd write. Even had the directory existed, AppArmor would have denied the queue files there. The fix is one word: workDirectory="/var/spool/rsyslog". After it, the only rsyslogd denial left in a boot journal is capability net_admin, three times, from a setsockopt(SO_RCVBUFFORCE) that rsyslog tries and does not need:

1
2

$ grep -a 'apparmor="DENIED".*rsyslogd' boot.journal.h1 | grep -o 'capname="[^"]*"' | sort | uniq -c
      3 capname="net_admin"

Harmless, and left alone.

On a freshly installed node of the current release it looks like this: the profile is enforced, rsyslogd runs under it with its RELP listener up, and that one capability is the only thing AppArmor denied it since boot.

The work directory is now pinned where the config is rendered: the third of the four unit tests of the syslog config greps the rendered rsyslog.conf for exactly that line.

What the lockdown was really testing

Enforcing a mandatory access control profile on a daemon is a test of every path that daemon is ever handed, and it runs at boot, not in the pipeline. The profile Ubuntu ships is right for the rsyslog Ubuntu ships. The moment I pointed rsyslog at my own CA directory and my own queue directory, I had changed what rsyslog is, and the profile needed to follow. The drop-in directory exists for precisely that, and it is the right place: the package file stays the package’s, my rules stay mine, an upgrade of the package replaces neither.

The part I would do differently is the check. “The message arrives on the control node” was the right end-to-end assertion, but it was run once, in the configuration of that week. The boot journal check is a cheaper one that runs every time and catches every daemon at once: if AppArmor denies something, the daemon says so, in a line with “error” or “DENIED” in it, and the test does not need to know what the daemon was trying to do. It found this one the first time it ran. The next post is about the line it found right after: rsyslog taking 90 s to stop, on the very forwarding that had just started working.

Takeaway

A feature that a security profile silently denies looks exactly like a feature that works, from everywhere except the journal. Read the daemon’s denials after every change to what it reads or writes, and keep a check in the pipeline that reads them for you. And when two errors appear together, fix the first and look again before believing the second was its child; mine was a wrong path in my own config, hiding behind a TLS failure it had nothing to do with.

The same profile that broke my forwarding is also the one doing its job. Here it is on a freshly installed node, with me as the attacker:

rsyslogd runs as root and listens on the network. If someone takes it over through a bug, they are root inside that process. aa-exec -p rsyslogd -- <command> runs a command with rsyslogd’s profile attached, so it stands in for that hijacked daemon. Line by line:

  1. id -un; wc -c /etc/ceph/ceph.client.admin.keyring: the baseline. I am root with no profile, and I can read the cluster’s admin keyring (83 bytes; wc -c has to read the file but prints none of it).
  2. aa-exec -p rsyslogd -- wc -c /etc/rsyslog.conf: the control. Under the profile, reading rsyslog’s own config still works, so the confined process is not simply blocked from everything.
  3. aa-exec -p rsyslogd -- wc -c /etc/ceph/ceph.client.admin.keyring: the theft. Same user, same file as in the first line, and now Permission denied: the profile does not list that path.
  4. aa-exec -p rsyslogd -- touch /usr/sbin/backdoor: the foothold. Planting a binary in a system directory is refused the same way.
  5. journalctl -b | grep 'apparmor="DENIED"': the kernel’s record of the two refusals, with the profile, the path, the command and what it asked for (r to read, c to create).
  6. ps -o user=,pid=,args= -C rsyslogd: the real daemon does run as root, so the stand-in was a fair one.

File permissions would have let both through: the keyring belongs to root, and so did the process. AppArmor is a second check the kernel makes after that one, and it asks a different question: not who the user is, but which program is asking, and whether that program’s profile lists the path. The profile is attached by the kernel when the program starts, the process cannot take it off from inside, and whatever it starts inherits it. A root shell I log into has no profile and reads the keyring freely; root inside rsyslogd does not.

That is the trade I had made without noticing: a daemon that can only touch what its profile lists is exactly a daemon that needs its profile updated when I hand it a new path.
