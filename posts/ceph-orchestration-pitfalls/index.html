Ceph Orchestration Pitfalls

Posted Sep 25, 2026
By Lee, Chien-Pang
18 min read

Cloud native tools usually give me excellent user experience that they feel like a plug and play, with cool out-of-the-box capabilities like auto deployments, scaling, healing, rolling-updates, etc. This ease of use convenience, however, is usually under the big assumption that it’s internet-reachable. This has always been my encounter with orchestration tools and infra. They are not air-gap friendly because you never know where the programs’/binaries’ default registries, mirrors or download values are hard-coded and if your overwrite settings are comprehensive enough that at some point the hidden misconfigurations would act up and block your way in a silent and hard-to-detect manner. My journey from Ceph native (legacy) to cephadm is no exception.

There are three main ways people manage Ceph, namely cephadm, Rook and legacy-native. Over the years I have been operating Ceph via the less favored approach, legacy-native - which is optimal for performance (without orchestration layer) and flexible in deployments as well as the granularities like how we want a bluestore/rocksdb to be partitioned or how to organize a disk into one or multiple osd, etc. Debugging a broken service is to me also straightforward but this is true since I am familiar with such bare-metal setups for long enough. An extra word on how old-fashioned I have been, I don’t even manage Ceph packages with Ansible, nor ceph-deploy. Everything is handled flat, rpm, systemd, monmap, keyring, mon, mgr, mds, rgw to partitioning disk and bringing up bluestore-backed osds, not to mention quorum establishment and version upgrades. All was well until loose ends appeared. I started to see outdated maintenance and operation scripts here and there that needed to be updated. The majority would eventually link to the final boss of all pains, “upgrade”, which has always been the biggest maintenance issue, keeping all things up to date IN TIME. Doing all the logistics is possible; nonetheless doing them fast is unlikely in a stretched release cycle. I cannot help but consider the orchestration path of managing Ceph storage.

Rook is immediately out of the choice list because I don’t have k8s infra for Rook to sit on top. Now cephadm is all that’s left; it is also the one that Ceph leans to. By the Octopus (v15.2.0) release back in 2020 cephadm was decided to be the future orchestrator. The biggest motivation was to fix a broken deployment ecosystem and fragmented tools such as ceph-deploy, ceph-ansible, ceph-volume, DeepSea, etc. That’s enough background. As I made up my mind and dug into the route to cephadm, things in general all moved on at a good pace until I hit an issue that baffled me.

Cutting the crap short, cephadm works like a charm when it’s Internet-reachable. This is generally the case for Cloud native technologies. But my ambition is to let it work in both Internet-reachable and air-gapped environments. cephadm works by running on top of containers (either Docker or Podman) which naturally depends on a Ceph image (quay.io/ceph/ceph:v20.2.0 as of this writing). Instead of hosting a registry for podman later to pull from, I go with skopeo

skopeo copy docker://$(CEPH_IMAGE) docker-archive:$(CEPH_IMAGE_PKG):$(CEPH_IMAGE)

To cut the story shorter, I managed to rule out hostname changes, including verifying if DNS resolution was playing the villain, and landed on another theory that there were some authentication errors based on logs. So I also went through the route of regenerating ssh keys, populating them so all mon, mgr, mds, rgw and osd can share and use them and verified SSH executions, key lookups and host scanning (all coming back: Ok 7 adapters detected: 7 rescanned).

As this is an air-gapped env., the original podman images of cephadm was imported from a static image. Certainly I have set the image to “ceph config set global container_image quay.io/ceph/ceph:v20.2.0”. Through the course of debugging, I then saw

Such trials and errors went on. Well, no. Nothing I did actually helped. I knew I was lost.

With AI tools’ help, I had also gone through these validations:

  • CherryPy shared-bus-restart theory?

By comparing closely the logs of working & failing Ceph cluster with orchestrator deployments, we saw the mgr’s cephadm module was seen restarting 3 times in a minute right around ceph_mgr_module_enable calls, theorizing dashboard/restful/prometheus sharing one HTTP engine disrupted the async loop. Disproven — reproduced identically on a fresh bootstrap with the dashboard never enabled and prometheus/telemetry explicitly disabled.

  • Direct syscall-level evidence (no py-spy/gdb/strace available offline)?

With agents doing monitoring work, they read /proc//syscall and /proc//task/*/syscall directly — 30 samples over 9s, full per-thread scan of ~175 mgr threads, everything parked on the same futex. Ruled out "actively blocked mid-DNS-lookup" and confirmed a stable deadlock, not a slow-but-progressing call.

  • Known upstream Ceph bug (found via web search)?

Still clueless, I couldn’t help but wondering if it’s actually a bug of this Ceph release. A bit of searching came back with some known issues of mgr/prometheus’s serve() doing a synchronous mon_command() with no timeout, capable of wedging the whole mgr (shared GIL). I didn’t enable prometheus anyway so there’s nothing concrete.

  • Root cause, found by source tracing (should’ve done this earlier :/). Extracted cephadm’s own zipapp (python3 -m zipapp) and grepped its mgr module source for the reconcile engine:
    • serve.py’s convert_tags_to_repo_digest() iterates every configured container_image (mon/mgr/mds plain tag quay.io/ceph/ceph:v20.2.0, not a digest) and calls _get_container_image_info() to resolve it — which needs to actually contact quay.io.
    • registry.py’s get_token() does requests.get(realm, params=params) with zero timeout — Python’s requests [does not enforce a default timeout] so, in a genuinely air-gapped network, this can hang forever, not just for a bounded DNS-retry window.
    • Manually testing cephadm inspect-image/cephadm –image … inspect-image (the fallback path) [worked correctly] — ruling out that specific path, but not the periodic re-resolution inside the normal reconcile loop.

Decisive confirmation: captured two full journalctl logs from the same deployment flow — once with internet up, once after cutting it — and diffed them. Both were byte-for-byte identical through the 5th cephadm-module reload’s ENGINE Bus STARTED line. Immediately after that: with internet, real daemon deploys began within seconds; without it, the cephadm-channel log simply stopped forever. This pinned the stall to exactly the transition where the orchestrator first needs to resolve an image reference — matching the convert_tags_to_repo_digest() finding.

I finally got a narrow enough clue that directly linked to our biggest suspect, Internet access. The image and digest. With further fiddling and poking I magically got the right configs I actually need

1
2

[h1 ~]# ceph config set global container_image <local-podman-image-id>
[h1 ~]# ceph config set mgr mgr/cephadm/use_repo_digest false

These 2 settings are the final piece of the puzzle

During the third or maybe fourth day when I was stuck by this issue, I had seriously considered if I should operate Ceph in dual modes, online with cephadm and offline with legacy but what if an online deployment decides to later go offline? I went back to Ceph’s documents which were positive about this direction of cephadm. It simply could not be true that such a bug exists without being screamed out in the public. Anyway, it’s gotta be my configs somewhere I ought to pursue. Now I have the honor (clear path) to explore more on how ceph orch works with auto scaling, upgrades and rolling-updates. The first noticeable gain, was ceph orch apply osd –all-available-devices which did all the heavy lifting work and brought the osds right up as shown in the screenshot above. This is a big advancement to me as opposed to legacy-native mode when I had to write all tools and functions to automate the whole disk preparation, partitioning, formatting, daemon services, key synching, /var/lib/ceph/osd arrangements, mounting, etc.
