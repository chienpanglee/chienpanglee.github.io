Have you got the time, Ceph?

Posted Nov 8, 2026
By Lee, Chien-Pang
5 min read
Have you got the time, Ceph?
Have you got the time, Ceph?

Have you got the time, Ceph? Ceph’s monitors refuse to work with a clock more than 0.05 s off (mon_clock_drift_allowed), and my own health check on the appliance flags a node past 10 s. So a node that is two minutes off is a node out of the cluster. At first glance this sounds like a corner case, but it has happened to me all the time since I enhanced my testing framework with RAM snapshots that seal a cluster topology (of one or more nodes). When a topology is restored, meaning the test VMs have been paused and resumed to a working state when snapshot was taken, chrony is running, it sees the gap, and it does nothing useful about it for as long as I watch.

Ceph is sensitive to clock skew because time is part of its coordination, authentication and failure-detection mechanisms. Ceph is a distributed system in which multiple MONs, MGRs, OSDs and MDSs must coordinate their decisions, and agreeing on the time plays a key role in that. Typical examples: the monitors compare their clocks and warn past 50 ms of drift, the Paxos leader grants the others a lease measured in seconds, and cephx tickets carry validity windows, so a node minutes off cannot even authenticate.

Let’s break it down.

  1. Ceph MON uses time to maintain cluster consistency Ceph MONs maintain cluster maps and consensus through the Paxos protocol.

For example, say a Ceph cluster has three MONs:

  • mon1
  • mon2
  • mon3 They maintain consistent versions of cluster maps, including:
  • OSDMap
  • MONMap
  • MDSMap
  • PGMap MONs use Paxos to agree on changes to cluster state.

If their clocks differ significantly, time-dependent operations can behave unexpectedly.

One particularly important mechanism is the MON clock-skew health check.

Ceph monitors compare their clocks and report MON_CLOCK_SKEW when they disagree.

What the monitors see: clock skew 120.024s > max 0.05s on one of three mons; everything else is healthy. Here is what my node looked like after a restore, with the stock chrony configuration:

Two seconds recovered in ninety. chrony was slewing: speeding the clock up by a bounded rate rather than jumping it. At that rate the node would have been back in a few hours.

The node 37 s after chronyd saw the gap: 117 s slow, Last offset -120 s, and the journal ends at System clock wrong by, no step.

makestep 1 3

Ubuntu’s stock /etc/chrony/chrony.conf ships:

1

makestep 1 3

Step the clock if the offset is over 1 s, but only during the first 3 clock updates after chronyd starts. After that, slew everything. That is a sensible default for a desktop, where a step after boot is startling and a big offset after boot means something is wrong. On a cluster node it means a gap that appears later, with chronyd already running, is never stepped. A paused VM, a suspended host, a hardware clock that lost a fight with firmware: all of them land in slew.

Two more things made it harder to see than it should have been.

The test that could not fail

My first end-to-end test for clock recovery moved the clock with date -s "+120 seconds" and waited for chrony to fix it. It passed with the stock config. It passed without any fix at all, because chronyd notices a jump of the system clock:

chronyd[1551]: Selected source h1
chronyd[1551]: System clock wrong by -120.339947 seconds
chronyd[1551]: System clock was stepped by -120.339947 seconds

A detected jump resets chrony’s sources, and the reset counts as a fresh start, so the “first 3 updates” window opens again and the gap is stepped. The test was reproducing a different fault from the one I had. A paused VM produces no jump event: from inside, time simply did not pass. « FIXME: need screenshot »

My second attempt matched the journal for System clock (wrong|was stepped). wrong by is logged on a slew too. Passed again, proved nothing again.

The honest reproduction pauses the VM from outside, over QMP (stop, 120 s, cont), with the stock config. That gives the wrong by line, no was stepped line, and 118 s slow ninety seconds later: the fault, in a test that goes red without the fix.

The fix, and where it has to live

1

makestep 1 -1

Step any offset over 1 s at any time. A step is the right call here: Ceph and the cluster manager tolerate a clock jump far better than minutes of skew, and the node is already unusable while it is off.

The obvious place for the override, /etc/chrony/conf.d/, does not work. The stock file has confdir /etc/chrony/conf.d on line 5 and makestep 1 3 on line 57; later directives win, so the stock line overrides anything in conf.d. The stock file itself has to change, which for an appliance means the image build edits it and checks that exactly one makestep line is left. The same test, with the fix:
