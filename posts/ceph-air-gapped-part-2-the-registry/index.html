Ceph Air-Gapped, Part 2: The Registry I Said I Didn't Need

Posted Oct 22, 2026
By Lee, Chien-Pang
6 min read
Ceph Air-Gapped, Part 2: The Registry I Said I Didn't Need
Ceph Air-Gapped, Part 2: The Registry I Said I Didn't Need

In my last post I spent days finding out why cephadm silently stalled in an air-gapped network, and the answer was two settings: point container_image at the image podman already had, and tell cephadm not to resolve tags into repo digests. An additional step that I adopted was that I did not run a registry. The Ceph image was copied with skopeo into an archive, shipped with the release, podman loaded on every node, and that was it. No extra service to keep alive, no credentials, nothing listening. The hassle of spinning up a private registry, pushing it in and then pulling it was avoided. A registry felt like exactly the kind of cloud-native furniture an offline appliance does not need.

That held up for a few weeks. Deploying worked, scaling out worked, and even an offline upgrade worked, because cephadm only pulls an image when the target digest is not already present on the host. Load the new image on every node first, run ceph orch upgrade start --image <digest>, and cephadm finds it locally and never asks the network. All verified working.

The red toast on the dashboard

Admittedly, UI was never my priority. Only late in the game did I fiddle with the Ceph dashboard, and I saw a warning that I couldn’t neglect. Every time the Overview page loaded, the first page after login or a click on the Ceph logo, a red toast popped up:

1

Failed to execute upgrade: Cannot get tags from url https://quay.io/v2/ceph/ceph/tags/list ... Name or service not known

The same toast, reproduced on a newer Ceph build (21.2.0).

Nothing was actually broken. The cluster was healthy, the storage served. But a red error on the first page an operator ever sees is not something I can ship, and it was the same type of problem as last time: something inside the orchestrator quietly assumes it can reach quay.io. Another pitfall in cloud-native images.

The dashboard’s Overview asks the orchestrator for available upgrades, and the CLI reproduces it directly:

The tags URL comes from the image’s repository name. I pin container_image to a digest, but a digest still carries its repository, quay.io/ceph/ceph@sha256:..., so the question still goes to quay.io.

Looking for a switch

My first hope was a setting, since that is how the last story ended. It was not this time.

  • The dashboard has feature toggles, but upgrades are not one of them. ceph dashboard feature status lists rbd, mirroring, iscsi, cephfs, rgw and nfs, nothing else, so I could not hide the panel.
  • ceph config ls | grep upgrade shows the upgrade knobs (parallel OSD upgrades, autoscaling during an upgrade, a CPU check), and grep registry shows the registry settings (registry_url, username, password, insecure, default_registry). None of them turns the tag lookup off.
  • A stub that answers that one dashboard endpoint would have hidden it in my demo setup and nowhere else.

At this point, what was in front of me were two choices: change upstream so the dashboard does not ask when the cluster is meant to be offline, or give it something local that answers /v2/ceph/ceph/tags/list. In other words, a registry. This is more of an exaggeration, but I felt sort of back to square one :/

The private registry, after all

The CNCF guidelines somewhere suggest running private registries in an offline env, but I still learned this the hard way. Once I accepted that, it stopped being a patch for one toast and became the simpler design for everything Ceph needs from an image:

1
2
3

online:   quay.io  --pull-->  local staging  --push-->  cluster registry
offline:  release  --unpack-> local staging  --push-->  cluster registry
then:     ceph orch upgrade start --image <registry>/ceph/ceph@sha256:<new>
  • One path for online and offline. cephadm, the dashboard and the upgrade always use the cluster’s own registry. Nodes never talk to quay.io themselves. The only difference between online and offline is how a new image gets into the registry.
  • Same bytes either way. The copy keeps the digest (skopeo copy --preserve-digests), and the digest is checked before the push, so an online node and an offline node run byte-identical images.
  • Every control node keeps a copy and serves it, with the virtual IP picking which one answers. A failover in the middle of an upgrade loses nothing.
  • Images live in storage that only moves forward. Ceph cannot be rolled back, so its images are never part of a snapshot that can be rolled back. Rolling back the OS or our own code never removes the image the cluster is running.
  • Old images go only after the upgrade has fully finished. Until then the cluster runs a mix of versions, and a daemon cephadm redeploys may still need the old one.

And, of course, the dashboard gets its answer from the local registry immediately: the tags it lists are exactly the ones the release shipped.

To be honest about where this stands: this is the decision, not the result. The registry is in the image but still switched off, and the toast still shows up on my test clusters. I will add the before and after once it runs.

Ceph gets its own update channel

The same discussion changed one more thing. I had planned for the Ceph image to travel only inside my own release packages: I test a Ceph version together with my code and ship them together. That stays the recommended path. But preparing a release package always takes longer than a podman pull, and Ceph, from what I have seen, works hard to keep point releases compatible. So an online operator may also pull a newer upstream stable release directly, as long as the tool says clearly what that means:

  • the version list shows only what can actually be applied: nothing older than what runs (Ceph only moves forward), no release candidates, at most two major releases ahead;
  • each version is marked tested or untested;
  • applying an untested one prints a warning that I have not tested it and that Ceph cannot be rolled back, and asks for an explicit yes.

A shortcut has its shortcomings

Last time I learned that “works offline” has to be tested by actually cutting the network, because the orchestrator hides its network calls well. This time I ran into the other half: avoiding a piece of infrastructure is not the same as not needing it. The registry I purposely left out came back through a side door, a dashboard panel I never asked for. Building it in on purpose gave me a simpler design than the workaround would have, one path for online and offline instead of two.
